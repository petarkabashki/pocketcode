## Clarifications

### Session 2026-03-07

- Q: What identifying information should the saved session list show? → A: Show each saved session with a title and last updated timestamp.
- Q: What scope should a tool approval decision apply to? → A: Approval applies only to the specific tool that was approved.
- Q: How should deletion of the currently active session be handled? → A: Do not allow deleting the currently active session.
- Q: Where should saved session history be available? → A: Saved sessions are available only within the current workspace.
- Q: How should session titles be assigned? → A: Titles are autogenerated by the system.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Scoped Tool Permission Choices (Priority: P1)

As a user, I want each tool execution approval prompt to offer one-time, session, and always choices so that I can control how long my approval lasts without being asked more often than necessary.

**Why this priority**: Tool approval prompts are part of the core interaction loop. If the available choices do not match the user’s intended trust level, the product feels repetitive for trusted tools and unsafe for sensitive actions.

**Independent Test**: Can be fully tested by triggering a tool approval prompt, choosing each approval scope in turn, and verifying that future approval behavior matches the chosen duration.

**Acceptance Scenarios**:

1. **Given** a tool requires user approval, **When** the approval prompt is shown, **Then** the prompt offers one-time, session, and always approval choices.
2. **Given** a user chooses one-time approval, **When** the same tool is requested again later, **Then** the system asks for approval again unless another approval scope has since been granted.
3. **Given** a user chooses session approval, **When** the same tool is requested again during the active session, **Then** the system proceeds without asking again for that session.
4. **Given** a user chooses always approval, **When** the same tool is requested in a later session, **Then** the system proceeds without asking again unless that persistent approval has been removed.
5. **Given** a user has approved one tool, **When** a different tool is requested, **Then** the system asks for approval unless that different tool has its own approval decision.

---

### User Story 2 - Resume or Start Sessions Intentionally (Priority: P1)

As a user, I want to start a new session or continue a previous session from a list of saved sessions so that I can either begin fresh or pick up prior work without losing context.

**Why this priority**: Session continuity directly affects productivity. Users need control over whether they continue existing work or intentionally separate a new task into a new session.

**Independent Test**: Can be fully tested by creating multiple sessions, confirming that prior sessions remain available, and selecting one of them to continue with its prior context intact.

**Acceptance Scenarios**:

1. **Given** a user has an active session, **When** they choose to start a new session, **Then** the system creates a separate session with an autogenerated title without overwriting or deleting previously saved sessions.
2. **Given** a user has one or more previous sessions in the current workspace, **When** they view session history, **Then** the system shows each saved session with a title and last updated timestamp so the user can choose the correct one.
3. **Given** a user selects a previous session, **When** the session is opened, **Then** the conversation continues in that session rather than starting from a blank state.

---

### User Story 3 - Remove Session History Safely (Priority: P2)

As a user, I want to delete an individual previous session or clear all previous sessions so that I can remove outdated or unwanted history without affecting sessions I intend to keep.

**Why this priority**: History management is necessary once sessions accumulate. Users need direct control over old sessions to keep the workspace organized and to remove history they no longer want retained.

**Independent Test**: Can be fully tested by deleting a specific saved session, confirming that only the selected session is removed, and then using clear-all to remove the remaining saved sessions.

**Acceptance Scenarios**:

1. **Given** multiple saved sessions exist, **When** a user deletes one specific session, **Then** only that session is removed and the others remain available.
2. **Given** saved sessions exist, **When** a user chooses to clear all previous sessions and confirms the action, **Then** all saved sessions are removed.
3. **Given** a user is managing session history, **When** they attempt a destructive session action, **Then** the system requires explicit confirmation before removing saved session data.

### Edge Cases

- A user may have no saved sessions; the system should still allow starting a new session and should present an empty-history state clearly.
- A saved session may be unavailable or unreadable; the system should identify that the session cannot be resumed and must not silently open the wrong session.
- A user may attempt to delete the session that is currently active; the system should block that action and keep the current session active.
- A user may choose session-scoped approval and then switch to a different session; the session-scoped approval must not carry over to another session.
- A user may choose clear-all when there are no previous sessions; the system should avoid destructive or confusing behavior and communicate that there is nothing to clear.
- A user may open a different workspace; saved sessions from the current workspace must not appear there.
- A persistent always approval may exist for a tool even after individual session history is deleted; persistent approvals and session history must not be conflated.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST present one-time, session, and always options whenever a tool execution request requires explicit user approval.
- **FR-001a**: The system MUST apply one-time, session, and always approval decisions only to the specific tool that was approved.
- **FR-002**: The system MUST define one-time approval as valid only for the current approval request.
- **FR-003**: The system MUST define session approval as valid only for the currently active session.
- **FR-004**: The system MUST define always approval as persistent across future sessions until it is explicitly removed.
- **FR-005**: The system MUST apply the chosen approval scope consistently when the same tool is requested again.
- **FR-006**: Users MUST be able to start a new session without overwriting or deleting previously saved sessions.
- **FR-007**: The system MUST retain previous sessions so users can review and select them later.
- **FR-008**: Users MUST be able to view a list of previous sessions and select one to continue.
- **FR-008a**: The system MUST show each saved session in the session list with a title and last updated timestamp.
- **FR-008b**: The system MUST make saved session history available only within the workspace where those sessions were created.
- **FR-008c**: The system MUST assign each new session an autogenerated title for display in session history.
- **FR-009**: The system MUST restore the selected previous session as the active session when the user chooses to continue it.
- **FR-010**: Users MUST be able to delete an individual saved session.
- **FR-011**: Users MUST be able to clear all previous saved sessions in a single action.
- **FR-012**: The system MUST require explicit confirmation before deleting an individual session or clearing all saved sessions.
- **FR-012a**: The system MUST NOT allow deletion of the currently active session.
- **FR-013**: The system MUST communicate the result of session creation, session selection, and session deletion actions clearly.
- **FR-014**: The system MUST prevent session-scoped approvals from applying to any session other than the one in which they were granted.
- **FR-015**: The system MUST keep persistent always approvals separate from saved session history so session deletion does not silently change persistent approval behavior.
- **FR-016**: The system MUST provide a clear empty state when no previous sessions are available to continue or delete.

### Key Entities *(include if feature involves data)*

- **Tool Approval Decision**: A user decision for a tool execution request, including the selected duration scope and the specific tool it applies to.
- **Session Record**: A saved conversation session that can be started, resumed, listed, or deleted, and includes an autogenerated title and last updated timestamp for user selection within its workspace.
- **Session History**: The workspace-scoped collection of saved session records available for selection and cleanup.
- **Active Session**: The session currently receiving user input and to which session-scoped approvals apply.

## Assumptions

- Session history refers to previously saved conversation sessions rather than transient view state.
- One-time, session, and always represent three distinct approval durations for tool execution decisions.
- Approval decisions are stored per tool and do not automatically extend to other tools.
- Users distinguish saved sessions using a title and last updated timestamp in the session list.
- Session titles are autogenerated by the system rather than entered manually when the session is created.
- Saved session history is isolated per workspace rather than shared globally across workspaces.
- Clear-all applies to saved previous sessions and does not implicitly remove persistent always approvals.
- The currently active session is excluded from deletion and clear-all history cleanup actions.
- Removing persistent always approvals is supported by an existing or future management surface outside the narrow scope of this request.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of tool approval prompts that require user consent present the three approval-duration choices: one-time, session, and always.
- **SC-002**: In validation tests, repeated tool requests follow the selected approval duration correctly in 100% of tested one-time, session, and always scenarios.
- **SC-003**: Users can start a new session or resume a previous one in under 30 seconds in a basic usability check.
- **SC-004**: 100% of previously saved sessions remain available after starting a new session unless the user explicitly deletes them.
- **SC-004a**: 100% of tested session history listings exclude sessions created in other workspaces.
- **SC-005**: 100% of tested individual-delete actions remove only the selected saved session.
- **SC-006**: 100% of tested clear-all actions remove all saved sessions only after explicit confirmation.
- **SC-007**: 100% of tested session-scoped approvals stop applying once the user leaves the session in which those approvals were granted.
